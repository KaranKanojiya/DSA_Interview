Core Idea

What is a Dynamic Array?

A resizable array that maintains a backing Object[] with a size (elements used) and capacity (array length). When size == capacity, it allocates a larger array and copies everything over.

The key insight: by growing multiplicatively (not by +1), the total copy cost is amortized O(1) per add.

Why build from scratch?

  • Tests understanding of amortized analysis
  • Explains why add() is O(1) despite occasional O(n) resizes
  • Foundation for StringBuilder, stack, and buffer implementations
  • Interviewers want to see the ensureCapacity → copy → grow pattern

Amortized Analysis

The Doubling Argument

Starting from capacity 1 and doubling each time, after n adds the total copy work is:

1 + 2 + 4 + 8 + ... + n = 2n - 1

Total work = n adds + 2n copies ≈ 3n. Divided by n operations = O(1) amortized per add.

Why Object[]? Java doesn't allow new E[] due to type erasure. Store as Object[] and cast on retrieval. Java's real ArrayList does the same.

add(index, element) — O(n)

insert at position
public void add(int index, E element) {
    if (index < 0 || index > size)
        throw new IndexOutOfBoundsException();
    ensureCapacity();
    // Shift elements right to make room
    System.arraycopy(data, index, data, index + 1, size - index);
    data[index] = element;
    size++;
}

get(index) — O(1)

random access
@SuppressWarnings("unchecked")
public E get(int index) {
    if (index < 0 || index >= size)
        throw new IndexOutOfBoundsException();
    return (E) data[index];
}

remove(index) — O(n)

shift left
@SuppressWarnings("unchecked")
public E remove(int index) {
    if (index < 0 || index >= size)
        throw new IndexOutOfBoundsException();
    E removed = (E) data[index];
    // Shift elements left to fill the gap
    System.arraycopy(data, index + 1, data, index, size - index - 1);
    data[--size] = null;   // prevent memory leak
    return removed;
}

public void set(int index, E element) {

ensureCapacity — Resize at 1.5×

growth
private void ensureCapacity() {
    if (size == data.length) {
        int newCapacity = data.length + (data.length >> 1); // 1.5× growth
        data = Arrays.copyOf(data, newCapacity);
    }
}
data.length >> 1 is integer division by 2. So length + length/2 = 1.5×. This is exactly what Java's ArrayList does internally.

Common Follow-ups

Should you shrink on remove?

Java's ArrayList does not auto-shrink. You can call trimToSize() manually. Auto-shrinking risks thrashing — repeated add/remove near the threshold causes repeated resize/shrink cycles. A common strategy: shrink when size drops below 25% of capacity.

Thread-safe alternatives?

Vector — synchronized on every method (coarse-grained, slow). CopyOnWriteArrayList — copies entire array on every write, great for read-heavy workloads. Collections.synchronizedList() — wrapper with global lock.

Why Object[] instead of E[]?

Java's type erasure means new E[n] is illegal at runtime — the JVM doesn't know what E is. Use new Object[n] and cast on retrieval with @SuppressWarnings("unchecked"). This is exactly how java.util.ArrayList is implemented.

ArrayList vs LinkedList?

ArrayList: O(1) random access, cache-friendly (contiguous memory), O(n) insert/remove at middle. LinkedList: O(1) insert/remove at ends, O(n) random access, poor cache locality. In practice, ArrayList wins almost always due to CPU cache effects.

Edge Cases & Gotchas

Index bounds check — get() and remove() check 0 ≤ index < size, but add(index) allows index == size (append). Getting this boundary wrong is a common bug.
Null out removed slot — After shifting elements left on remove, set data[--size] = null. Without this, the old reference prevents garbage collection — a subtle memory leak.
Resize during add(index) — Must call ensureCapacity() before the arraycopy shift. Otherwise, if the array is full, the shift would overflow. Our code handles this correctly.
