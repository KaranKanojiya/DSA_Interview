Core Idea

What is Producer-Consumer?

A concurrency pattern where producer threads generate work items and place them into a shared bounded buffer, while consumer threads take items out and process them.

The buffer decouples production speed from consumption speed — classic backpressure.

Why bounded buffer?

  • Backpressure — producers slow down when buffer is full, preventing OOM
  • Decoupling — producers and consumers run at independent rates
  • Thread safety — all access via synchronized + wait/notifyAll
  • Foundation for BlockingQueue, thread pools, and message brokers

wait/notifyAll vs Lock/Condition

synchronized + wait/notifyAll

  • Simpler — built into every Java object
  • Single condition: all waiters share one wait-set
  • Must use notifyAll() to avoid lost wakeups
  • Good for simple producer-consumer

This is what our implementation uses.

Lock + Condition

  • More flexible — multiple Conditions per Lock
  • Separate notFull and notEmpty conditions
  • Can use signal() instead of signalAll()
  • Better for complex coordination

Used in MyBlockingQueue in this repo.

Why while-loop, not if? Spurious wakeups can occur — the thread may be woken without the condition actually changing. The while loop rechecks the condition after every wakeup, making the code safe from spurious wakeups and race conditions.

Real-World Examples

Kafka / Message Queues

Producers write messages to topic partitions (bounded by retention/memory). Consumers poll messages. Backpressure via broker-side buffering.

Thread Pools

ThreadPoolExecutor uses a BlockingQueue internally. Submitted tasks are "produced" into the queue; worker threads "consume" them. Bounded queue = backpressure.

Logging Frameworks

Log4j2 AsyncAppender: application threads produce log events, background thread consumes and writes to disk. Bounded ring buffer prevents OOM.

Pipeline Processing

ETL pipelines where Stage 1 produces records, Stage 2 transforms, Stage 3 loads. Each stage is a consumer of the previous and producer for the next.

BoundedBuffer — Inner Class

core structure

A generic bounded buffer backed by a Queue with a fixed capacity. All operations are synchronized on the buffer instance.

static class BoundedBuffer<E> {
    private final Queue<E> queue = new LinkedList<>();
    private final int capacity;

    BoundedBuffer(int capacity) { this.capacity = capacity; }
}
2

produce() — Add Item

blocks when full

If the buffer is at capacity, the producer thread releases the monitor and waits. Once space is available, it adds the item and wakes all waiting threads.

synchronized void produce(E item) throws InterruptedException {
    // Guard: block while buffer is full
    while (queue.size() == capacity) {
        wait();             // release lock, sleep until notified
    }
    queue.add(item);        // enqueue the item
    System.out.println("  Produced: " + item + " | size=" + queue.size());
    notifyAll();            // wake consumers (and other producers)
}
3

consume() — Take Item

blocks when empty

Mirror of produce: consumer waits while empty, then polls and wakes all threads so a blocked producer can proceed.

synchronized E consume() throws InterruptedException {
    // Guard: block while buffer is empty
    while (queue.isEmpty()) {
        wait();             // release lock, sleep until notified
    }
    E item = queue.poll();  // dequeue the item
    System.out.println("  Consumed: " + item + " | size=" + queue.size());
    notifyAll();            // wake producers (and other consumers)
    return item;
}

main() — Demo with 2 Threads

demo

Producer generates items faster (50ms sleep) than consumer processes them (150ms sleep), showing the buffer filling up and producer eventually blocking.

public static void main(String[] args) throws InterruptedException {
    BoundedBuffer<Integer> buffer = new BoundedBuffer<>(3);

    Thread producer = new Thread(() -> {
        try {
            for (int i = 1; i <= 6; i++) {
                buffer.produce(i);
                Thread.sleep(50);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });

    Thread consumer = new Thread(() -> {
        try {
            for (int i = 0; i < 6; i++) {
                buffer.consume();
                Thread.sleep(150);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });

    producer.start(); consumer.start();
    producer.join(); consumer.join();
}

Common Follow-ups

Multiple producers & consumers?

Works as-is because synchronized + while-loop guards are thread-safe for any number of threads. Each call to notifyAll() wakes all waiters; the while loop ensures only one proceeds when the condition is met. For better throughput, consider separate locks for produce/consume (like ReentrantLock with two Conditions).

Poison pill shutdown?

Producer sends a special sentinel value (e.g., null or Integer.MIN_VALUE) to signal consumers to stop. Each consumer, upon receiving the poison pill, re-inserts it (so other consumers also see it) and exits its loop. Cleaner than Thread.interrupt() for graceful shutdown.

Priority queue variant?

Replace LinkedList with a PriorityQueue (min-heap). Produce still O(log n) due to heap insertion. Consumer gets the highest-priority item. Useful for task schedulers where urgent tasks should be processed first.

Compare to BlockingQueue?

Java's ArrayBlockingQueue uses ReentrantLock with separate notFull/notEmpty conditions — more efficient because signal() targets only the right waiter type. Our notifyAll() wakes everyone including irrelevant threads. This repo's MyBlockingQueue shows the Lock/Condition version.

Edge Cases & Gotchas

notify vs notifyAll — Using notify() instead of notifyAll() can cause lost wakeups. If a producer notifies and the woken thread is another producer (not a consumer), the consumer never wakes. Always use notifyAll() when multiple thread types share one monitor.
Single producer, many consumers — Works correctly, but consumers compete. Only one consumer holds the lock at a time. If buffer frequently empty, most consumers spend time waiting — consider multiple buffers or work-stealing.
Buffer size = 1 — Degenerates into strict alternation: produce → consume → produce → consume. Essentially a synchronous handoff (like SynchronousQueue). Minimal buffering, maximum coupling.
while vs if — Using if instead of while before wait() is a classic bug. Spurious wakeups or multiple consumers waking simultaneously can lead to consuming from an empty queue or producing into a full one.
