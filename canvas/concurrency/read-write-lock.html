Core Idea

What is a ReadWrite Lock?

A lock that distinguishes between read and write access. Reads don't modify shared state, so multiple readers can proceed concurrently. Writes need exclusive access.

Optimizes for read-heavy workloads — databases, caches, config stores.

When to use RWLock vs Mutex?

  • RWLock — read-heavy workloads (90%+ reads). Multiple readers run in parallel.
  • Mutex — write-heavy workloads or balanced. Simpler, less overhead per acquisition.
  • RWLock has higher overhead per operation — only pays off when reads vastly outnumber writes.

Writer Starvation Problem & Fix

Problem (without fix)

If readers keep arriving, the reader count never drops to 0. The writer waits forever — starvation.

Scenario: Reader 1 holds lock → Reader 2 arrives (allowed) → Writer waits → Reader 3 arrives (allowed) → Reader 1 leaves → Reader 4 arrives … writer never gets in.

Fix: writersWaiting counter

When a writer is waiting, new readers also wait. Existing readers finish, then the writer gets in.

readLock() checks: while (writerActive || writersWaiting > 0) wait(). New readers yield to waiting writers.

2

readLock()

shared acquisition

Wait while a writer is active OR writers are waiting (starvation prevention). Then increment reader count.

public synchronized void readLock() throws InterruptedException {
    // Block if writer is active OR if writers are waiting (prevent starvation)
    while (writerActive || writersWaiting > 0) {
        wait();
    }
    readers++;
}
3

readUnlock()

shared release

Decrement reader count. If this was the last reader, notify all — a waiting writer can now proceed.

public synchronized void readUnlock() {
    readers--;
    if (readers == 0) {
        notifyAll();  // wake waiting writer (if any)
    }
}
4

writeLock()

exclusive acquisition

Increment writersWaiting (blocks new readers), wait until no readers and no active writer, then acquire.

public synchronized void writeLock() throws InterruptedException {
    writersWaiting++;  // signal to readLock: "a writer is waiting, don't enter"
    while (readers > 0 || writerActive) {
        wait();  // wait until all readers finish AND no other writer active
    }
    writersWaiting--;
    writerActive = true;
}
5

writeUnlock()

exclusive release

Clear writer flag and wake all waiting threads — both readers and writers compete for the lock.

public synchronized void writeUnlock() {
    writerActive = false;
    notifyAll();  // wake ALL waiting threads (readers + writers)
}
Why notifyAll() (not notify())? After a writer releases, multiple readers can proceed simultaneously. notify() would wake only one thread — potentially a single reader when many readers could run concurrently.

Common Follow-ups

ReentrantReadWriteLock?

Java's built-in version uses a single int state: upper 16 bits = read count, lower 16 bits = write count. Supports reentrancy (same thread can acquire multiple times), optional fairness, and lock downgrading (write → read without releasing).

StampedLock optimistic read?

StampedLock.tryOptimisticRead() returns a "stamp" without acquiring any lock. After reading shared data, call validate(stamp) — if no writer intervened, the read is valid. Falls back to a full read lock if validation fails. Much faster for read-heavy scenarios.

Downgrade write → read?

While holding write lock: acquire read lock, then release write lock. This allows the thread to keep read access while letting other readers in. ReentrantReadWriteLock supports this. The reverse (read → write upgrade) is NOT safe — can cause deadlock if two readers both try to upgrade.

Fairness considerations?

Our implementation is writer-preferring: when writersWaiting > 0, new readers wait. Alternative: reader-preferring (new readers always proceed — writers may starve) or fair (FIFO queue order — most expensive). Java's ReentrantReadWriteLock(true) gives fair ordering.

3

Edge Cases & Gotchas

Writer starvation without counter — Without writersWaiting, a continuous stream of readers prevents the writer from ever acquiring the lock. Always include a mechanism to give writers priority when they're waiting.
Read-then-write upgrade deadlock — Thread A holds read lock, tries to acquire write lock → waits for readers to reach 0 → but A itself is a reader → deadlock. The solution: release read lock first, then acquire write lock (but this creates a gap where data may change).
readUnlock only notifies when readers == 0 — No point waking a writer when other readers are still active. This optimization avoids unnecessary context switches. Only the last reader triggers notifyAll.
Why synchronized works here — Unlike BlockingQueue (which needs two wait sets), RWLock only needs one: both readers and writers check their conditions in while loops after notifyAll wakes them. The simplicity of synchronized is sufficient.
