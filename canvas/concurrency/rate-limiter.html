Core Idea

What is Rate Limiting?

Restrict the number of requests a client can make within a time window. Example: max 5 requests per second per user.

  • Protects servers from abuse and overload
  • Ensures fair resource sharing across clients
  • Required by API gateways, CDNs, auth systems

Two Algorithms

  • Token Bucket — bucket fills at a rate, each request drains one token. No tokens = denied. Allows bursts up to capacity.
  • Sliding Window Log — store timestamp of each request. Remove old ones. Count remaining. Exact but uses more memory.

Token Bucket is the industry standard (AWS, Stripe, Google). Sliding Window is simpler to reason about.

Token Bucket — Fields & Constructor

algorithm 1
static class TokenBucket {
    private final int capacity;          // max tokens the bucket can hold
    private final double refillRate;     // tokens added per second
    private double tokens;               // current available tokens
    private long lastRefillTime;          // when we last added tokens

    TokenBucket(int capacity, double refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.tokens = capacity;              // start full
        this.lastRefillTime = System.nanoTime();
    }
}

Token Bucket — allowRequest()

O(1)

Lazy refill: calculate tokens earned since last call, then check if we have enough. No background thread needed.

synchronized boolean allowRequest() {
    refill();  // add tokens based on elapsed time

    if (tokens >= 1.0) {
        tokens -= 1.0;    // consume one token
        return true;       // allowed
    }
    return false;          // denied — no tokens available
}

// Lazy refill — calculate tokens earned since last check
private void refill() {
    long now = System.nanoTime();
    double elapsed = (now - lastRefillTime) / 1_000_000_000.0;  // seconds
    double newTokens = elapsed * refillRate;

    // Add tokens but don't exceed capacity (bucket has a max)
    tokens = Math.min(capacity, tokens + newTokens);
    lastRefillTime = now;
}

Sliding Window Log — allowRequest()

O(n) worst

Remove expired timestamps from the front of the deque, then check if we're under the limit.

synchronized boolean allowRequest() {
    long now = System.currentTimeMillis();
    long windowStart = now - windowSizeMs;

    // Remove timestamps outside the window (older than windowStart)
    while (!timestamps.isEmpty() && timestamps.peekFirst() <= windowStart) {
        timestamps.pollFirst();
    }

    // Check if we're under the limit
    if (timestamps.size() < maxRequests) {
        timestamps.addLast(now);  // record this request
        return true;              // allowed
    }
    return false;                 // denied — window full
}

Common Follow-ups

Distributed rate limiter with Redis?

Store token count or window in Redis. Use Lua scripts for atomic check-and-decrement (EVAL ensures atomicity). Alternative: Redis INCR + EXPIRE for fixed window. Stripe and Cloudflare use Redis + Lua for their rate limiters. Key pattern: rate:{userId}:{windowId}.

Fixed window counter?

Divide time into fixed windows (e.g., each second). One counter per window, reset at window boundary. Problem: a burst at window end + burst at next window start = 2x the limit. Simple and O(1) but imprecise at boundaries.

Sliding window counter (hybrid)?

Combine fixed window counter with weighted overlap. count = prevWindow × overlapRatio + currentWindow. Example: 70% into current window → prev × 0.3 + current. O(1) time and space, smoother than fixed window, used by Cloudflare.

Per-user rate limiting?

Use Map<String, RateLimiter> keyed by user ID. Lazy-create limiter on first request. Need a cleanup mechanism for inactive users (LRU eviction or TTL). In production, store in Redis with user-specific keys.

Edge Cases & Gotchas

Clock precision — Token Bucket uses System.nanoTime() (monotonic, high resolution) for elapsed time calculation. currentTimeMillis() can jump due to NTP clock adjustments. Sliding Window uses millis because it stores wall-clock timestamps for window comparison.
Burst handling — Token Bucket allows a burst of up to capacity requests instantly (if bucket is full). If you need strict per-second limits without bursts, use Sliding Window Log or set bucket capacity = 1 second's worth of tokens.
Lazy refill is key — No background thread calculating tokens. The refill() method is called inside allowRequest(), computing tokens based on elapsed time. This makes the implementation stateless between calls — much simpler than a timer-based approach.
tokens as double — Using double instead of int allows fractional token accumulation. With refillRate=2.5, after 0.4 seconds you'd have 1.0 token. Integer math would lose this precision and break sub-second refill rates.
synchronized on both classes — Both allowRequest() methods are synchronized for thread safety. In a high-throughput system, consider AtomicLong + CAS loop to avoid lock contention, or per-user locks to reduce lock scope.
