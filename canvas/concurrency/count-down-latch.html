Core Idea

What is a CountDown Latch?

A gate that stays closed until a counter reaches zero. Worker threads call countDown() to decrement the counter. Waiting threads call await() and block until the gate opens (count = 0).

Once opened, the gate stays open forever — a latch is one-shot.

Why build from scratch?

  • Tests understanding of synchronized + wait/notifyAll
  • Simple but reveals edge cases: count=0 at start, multiple awaiters
  • Leads to follow-up: "now implement CyclicBarrier" (reusable)
  • Only ~20 lines of logic — but the concurrency reasoning matters

One-Shot vs Reusable

CountDownLatch (one-shot)

  • Count goes down to 0, gate opens permanently
  • Cannot be reset — create a new instance
  • N workers count down, M threads await
  • Use: "wait for N tasks to finish"

CyclicBarrier (reusable)

  • All N threads must arrive at the barrier
  • Resets after all threads pass — reusable for rounds
  • All threads wait for each other (symmetric)
  • Use: "all threads synchronize at a checkpoint"
Key difference: CountDownLatch is asymmetric (some threads count down, others await). CyclicBarrier is symmetric (all threads wait for each other). Phaser combines both and supports dynamic registration.

Real-World Uses

Service Startup

Main thread creates latch(N) where N = number of subsystems. Each subsystem signals ready via countDown(). Server begins accepting requests only after await() returns.

Parallel Test Coordination

Launch N threads, have them all wait on a "start" latch(1). Test driver calls countDown() and all threads race simultaneously — ensures a true concurrent start.

Map-Reduce Barrier

Map phase: each mapper counts down when done. Reduce phase: awaits all mappers. Simple barrier for batch parallel processing.

Health Check Gate

Microservice waits for DB, cache, and message broker connections before marking itself healthy. Latch(3), each dependency counts down on connect.

countDown() — Decrement

worker calls this

Decrements count. When it hits zero, notifyAll() wakes every thread blocked in await(). Calling countDown() when already zero is a no-op — safe and idempotent.

public synchronized void countDown() {
    if (count > 0) {
        count--;
        if (count == 0) {
            notifyAll();   // wake all waiting threads
        }
    }
}
3

await() — Block Until Zero

main thread calls this

Blocks the calling thread until count reaches zero. Uses while loop to guard against spurious wakeups. If count is already zero, returns immediately.

public synchronized void await() throws InterruptedException {
    while (count > 0) {
        wait();            // release monitor, sleep until notified
    }
}

main() — Demo

demo

3 worker threads count down at staggered intervals. Main thread waits, then continues after all workers finish.

public static void main(String[] args) throws InterruptedException {
    MyCountDownLatch latch = new MyCountDownLatch(3);

    for (int i = 1; i <= 3; i++) {
        final int id = i;
        new Thread(() -> {
            try { Thread.sleep(id * 200); }
            catch (InterruptedException e) {}
            System.out.println("  Worker " + id + " done → countDown()");
            latch.countDown();
        }).start();
    }

    System.out.println("Main thread waiting...");
    latch.await();
    System.out.println("All workers done — main thread continues!");
}

Common Follow-ups

CyclicBarrier vs CountDownLatch vs Phaser?

FeatureCountDownLatchCyclicBarrierPhaser
Reusable?No (one-shot)Yes (auto-reset)Yes (phases)
Who waits?Separate awaitersAll participantsRegistered parties
Dynamic parties?NoNoYes (register/deregister)
Barrier action?NoOptional RunnableOptional onAdvance()

Implement CyclicBarrier?

Track parties (total) and waiting (arrived). Each thread increments waiting and calls wait(). When waiting == parties, run the barrier action, reset waiting = 0, and notifyAll(). Use a generation counter to handle the reset cycle correctly — threads from different rounds must not interfere.

Phaser — the flexible version?

Phaser supports dynamic registration (register() / arriveAndDeregister()), multiple phases, and hierarchical phasers for scalability. It's the most flexible but also the most complex. Think of it as a reusable latch where the number of participants can change between rounds.

Await with timeout?

Add an overload: await(long timeout, TimeUnit unit). Use wait(millis) with a deadline. After waking, check if count is 0 OR the deadline has passed. Return boolean indicating whether count reached zero. Java's real CountDownLatch supports this.

Edge Cases & Gotchas

count = 0 at start — await() returns immediately. The while-loop condition count > 0 is false from the start. This is valid and intentional — useful for conditional coordination where sometimes no waiting is needed.
Multiple await callers — Multiple threads can call await(). When count hits zero, notifyAll() wakes all of them. All proceed simultaneously. This is by design — latches are "one-to-many" gates.
countDown below 0 — Our implementation guards with if (count > 0), so extra countDown calls are harmless no-ops. Without this guard, count could go negative, and the latch would still work (while-loop checks count > 0), but negative count is semantically wrong.
Cannot reset — Unlike CyclicBarrier, a latch that has reached zero stays at zero forever. Any future await() call returns immediately. To "reset", create a new MyCountDownLatch instance.
