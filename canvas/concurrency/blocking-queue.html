Core Idea

What is a Blocking Queue?

A bounded, thread-safe queue where:

  • put(item) blocks the caller when the queue is full — waits until space is available
  • take() blocks the caller when the queue is empty — waits until an item is available

This blocking behavior is what makes the producer-consumer pattern work without busy-waiting.

Why TWO Conditions (not one)?

  • One condition + notifyAll() → wakes ALL threads (producers AND consumers) — wasteful
  • Two conditions → notFull.signal() wakes only a producer, notEmpty.signal() wakes only a consumer
  • Targeted signaling = fewer wasted context switches

ReentrantLock supports multiple Condition objects; synchronized only has one wait set.

Spurious Wakeups — WHILE not IF

Wrong: IF

if (queue.size() == capacity)
    notFull.await();
// ⚠️ might wake up without signal
// queue could STILL be full!

Correct: WHILE

while (queue.size() == capacity)
    notFull.await();
// ✓ re-checks condition after wakeup
// loops back if still full
Spurious wakeup: OS/JVM can wake a thread from await() without any signal() call. The WHILE loop re-checks the condition, making the code correct regardless. This is a Java specification requirement.

Fields & Constructor

setup
private final Queue<E> queue;
private final int capacity;

// ReentrantLock — explicit lock (more flexible than synchronized)
private final ReentrantLock lock = new ReentrantLock();

// Two conditions for targeted signaling:
private final Condition notFull  = lock.newCondition();  // producers wait here
private final Condition notEmpty = lock.newCondition();  // consumers wait here

public MyBlockingQueue(int capacity) {
    this.capacity = capacity;
    this.queue = new LinkedList<>();
}

put(item) — Blocks if Full

producer

Called by producer threads. Acquires lock, waits in a WHILE loop if queue is full, adds item, signals one consumer.

public void put(E item) throws InterruptedException {
    lock.lock();
    try {
        // WHILE loop — guard against spurious wakeups
        while (queue.size() == capacity) {
            notFull.await();  // release lock + wait → re-acquire when signaled
        }

        queue.add(item);

        // Signal ONE waiting consumer: "there's an item for you"
        notEmpty.signal();
    } finally {
        lock.unlock();  // ALWAYS unlock in finally — even if exception thrown
    }
}
3

take() — Blocks if Empty

consumer

Called by consumer threads. Acquires lock, waits if queue is empty, removes item, signals one producer.

public E take() throws InterruptedException {
    lock.lock();
    try {
        // Wait while empty
        while (queue.isEmpty()) {
            notEmpty.await();  // release lock + wait → re-acquire when signaled
        }

        E item = queue.poll();

        // Signal ONE waiting producer: "there's space for you"
        notFull.signal();

        return item;
    } finally {
        lock.unlock();
    }
}

size()

thread-safe read
public int size() {
    lock.lock();
    try { return queue.size(); }
    finally { lock.unlock(); }
}

Common Follow-ups

Priority blocking queue?

Replace LinkedList with a min-heap (PriorityQueue). put() does heap-insert O(log n), take() does heap-extract O(log n). Still uses the same Lock + two Conditions pattern. Java's PriorityBlockingQueue is unbounded — it never blocks on put.

Multiple producers / consumers?

Works correctly as-is. The ReentrantLock ensures mutual exclusion. signal() wakes exactly one waiting thread. With many producers, notFull.signal() wakes one producer — others stay asleep. No thundering herd problem.

Backpressure strategy?

Blocking on put() IS backpressure — producer slows down naturally. Alternatives: offer(item, timeout) returns false instead of blocking forever, letting the producer decide (drop, retry, log). In reactive systems, use flow control signals.

ArrayBlockingQueue vs LinkedBlockingQueue?

Array: fixed-size circular buffer, single lock, better cache locality, pre-allocated memory. Linked: optionally unbounded, two separate locks (put/take can proceed simultaneously), higher memory overhead from node objects. Array is usually better for bounded queues.

Edge Cases & Gotchas

Spurious wakeup — Using if instead of while before await() is the #1 bug. The JVM spec says threads CAN wake without a signal. Always re-check the condition in a loop.
Interrupt during await() — await() throws InterruptedException. The lock is automatically re-acquired before the exception propagates. Propagate the interrupt properly (re-throw or set interrupt flag).
Always unlock in finally — If lock.unlock() is not in a finally block, any exception between lock() and unlock() causes a permanent deadlock. Every other thread waiting for this lock will hang forever.
signal() vs signalAll() — signal() wakes ONE thread (efficient). signalAll() wakes ALL (safe but wasteful). Use signal() when you know exactly one thread can proceed — which is the case here since we add/remove one item at a time.
Why not synchronized? — synchronized blocks have only ONE implicit wait set. You can't separate producer waits from consumer waits. notifyAll() wakes everyone — producers AND consumers — even though only one type can proceed.
