Core Idea

What is a Semaphore?

A permit counter. Threads must acquire a permit before accessing a resource. If no permits are available, the thread blocks. When done, the thread releases the permit for others to use.

Think of it as a parking lot: N spots (permits). Cars (threads) enter when spots are available, wait when full.

Binary vs Counting Semaphore

  • Binary (permits=1) — acts like a mutex. Only one thread at a time.
  • Counting (permits=N) — up to N threads concurrently. Used for connection pools, rate limiting.
  • Unlike a mutex, any thread can release — not just the owner
  • tryAcquire() adds non-blocking semantics

Mutex vs Semaphore

Mutex (Lock)

  • Ownership — only the thread that locked can unlock
  • Binary: locked or unlocked
  • Supports reentrance (same thread locks multiple times)
  • Use: protecting critical sections

Semaphore

  • No ownership — any thread can release
  • Counting: 0 to N permits
  • Not reentrant — acquiring twice uses two permits
  • Use: limiting concurrency, resource pooling
Binary semaphore ≠ mutex. A binary semaphore (permits=1) looks like a mutex but has no ownership. Thread A can acquire, Thread B can release. This makes semaphores useful for signaling between threads, but dangerous if you need ownership semantics.

Real-World Uses

Connection Pools

Database connection pool with N connections. Semaphore(N) — each acquire() borrows a connection, release() returns it. Prevents creating more connections than the pool size.

Rate Limiting

API rate limiter: Semaphore(maxConcurrent). Each incoming request acquires a permit. If all permits are taken, request blocks or gets rejected (tryAcquire). Completed requests release permits.

Thread Throttling

Control parallelism in a thread pool. Even with 100 threads, limit actual concurrent DB/IO operations to 10 using Semaphore(10).

Print Queue / Resource Scheduling

N printers shared by many users. Semaphore(N). Users acquire a printer, print, release. Classic OS textbook example of semaphore usage.

acquire() — Blocking

takes a permit

Blocks if no permits available. Uses while loop for spurious wakeup safety. Decrements permits when one becomes available.

public synchronized void acquire() throws InterruptedException {
    while (permits == 0) {
        wait();            // release monitor, sleep until notified
    }
    permits--;             // take the permit
}
3

release() — Return Permit

gives back a permit

Increments permits and wakes one waiting thread. Uses notify() (not notifyAll) — only one waiter can use the released permit.

public synchronized void release() {
    permits++;             // return the permit
    notify();              // wake one waiting thread
}
4

tryAcquire() — Non-Blocking

try without waiting

Attempts to acquire a permit without blocking. Returns true if successful, false otherwise. Useful for graceful degradation or timeout patterns.

public synchronized boolean tryAcquire() {
    if (permits > 0) {
        permits--;
        return true;
    }
    return false;
}

public synchronized int availablePermits() {

main() — Demo

demo

5 threads compete for 2 permits. Only 2 run concurrently at any time. Each thread acquires, sleeps (simulating work), then releases.

public static void main(String[] args) throws InterruptedException {
    MySemaphore sem = new MySemaphore(2);  // only 2 concurrent accesses

    for (int i = 1; i <= 5; i++) {
        final int id = i;
        new Thread(() -> {
            try {
                sem.acquire();
                System.out.println("  Thread " + id + " acquired (permits="
                    + sem.availablePermits() + ")");
                Thread.sleep(300);
                sem.release();
                System.out.println("  Thread " + id + " released");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }).start();
    }

    Thread.sleep(2000);
    System.out.println("\nOnly 2 threads run concurrently — others wait for permits");
}

Common Follow-ups

Fair semaphore with FIFO queue?

Our implementation is unfair — a newly arriving thread can steal a permit before a thread that has been waiting longer. For fairness, maintain a FIFO queue of waiting threads. On release(), wake the thread at the head of the queue. Java's Semaphore(permits, true) uses an internal AbstractQueuedSynchronizer (AQS) with a CLH queue for FIFO ordering.

Dining Philosophers?

Classic deadlock problem: 5 philosophers, 5 forks. One solution: use a Semaphore(4) to limit concurrent diners to 4, guaranteeing at least one philosopher can eat. Alternative: ordered resource acquisition (always pick lower-numbered fork first) or use a ReentrantLock with tryLock() for timeout-based deadlock avoidance.

Reader-Writer with Semaphores?

Use two semaphores: readMutex (binary, protects reader count) and writeLock (binary, exclusive write access). Readers: increment count under readMutex, first reader acquires writeLock, last reader releases it. Writers: acquire writeLock directly. This gives reader-preference; for writer-preference, add a third semaphore.

Connection pool using semaphore?

Pool of N connections, Semaphore(N). borrow(): acquire permit, then take connection from a concurrent queue. returnConn(): put connection back in queue, release permit. The semaphore prevents borrowing when all connections are in use. tryAcquire(timeout) enables fail-fast when pool is exhausted.

Edge Cases & Gotchas

release without acquire inflates permits — Since there's no ownership tracking, calling release() without a prior acquire() increases permits beyond the initial value. This is a feature in signaling scenarios but a bug in resource pooling. To prevent, track acquired state per thread or add validation.
permits = 0 initial — All threads block immediately on acquire(). Useful for signaling: another thread calls release() to unblock one waiter. This turns the semaphore into a one-shot signal (like a simplified latch for one thread).
notify() vs notifyAll() — Our release() uses notify() (not notifyAll). This is safe here because each release() only frees one permit — waking one waiter is sufficient. If we released multiple permits at once, we'd need notifyAll().
Interrupt during wait — wait() throws InterruptedException if the thread is interrupted while waiting. Our acquire() propagates it. Callers should handle interruption gracefully — typically by restoring the interrupt flag and cleaning up.
