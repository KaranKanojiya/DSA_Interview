Core Idea

What is Pub/Sub?

A messaging pattern where publishers send messages to named topics, and subscribers register handlers for topics they care about. The pub/sub system acts as a broker — neither side knows about the other.

Real-world: Kafka, AWS SNS/SQS, Google Pub/Sub, Redis pub/sub.

Pub/Sub vs Observer

  • Observer: synchronous, subject calls observers directly
  • Pub/Sub: async via broker, full decoupling
  • Pub/Sub adds: topic routing, thread pool delivery, thread safety
  • Pub/Sub is the distributed version of Observer

Thread Safety — Why ConcurrentHashMap + CopyOnWriteArrayList

ConcurrentHashMap

  • Thread-safe map — multiple threads can subscribe/publish concurrently
  • Lock striping — segments lock independently
  • computeIfAbsent is atomic — no race on first subscribe

CopyOnWriteArrayList

  • Thread-safe list — iteration never throws CME
  • Writes create a new copy of the array
  • Perfect for read-heavy workloads (many publishes, rare subscribes)
Why not synchronized? A global lock would serialize all publish/subscribe calls. ConcurrentHashMap allows concurrent access to different topics. CopyOnWriteArrayList allows safe iteration during publish while another thread subscribes.

private final Map<String, List<Consumer<String>>> subscribers
        = new ConcurrentHashMap<>();
private final ExecutorService executor

Consumer<String> — Handlers are simple functions that accept a message string. This makes subscribing with lambdas natural: bus.subscribe("orders", msg -> ...).

register
public void subscribe(String topic, Consumer<String> handler) {
    subscribers.computeIfAbsent(topic, k -> new CopyOnWriteArrayList<>())
               .add(handler);
}
3

publish(topic, message) — Async Delivery

core logic
public void publish(String topic, String message) {
    for (Consumer<String> handler :
            subscribers.getOrDefault(topic, List.of())) {
        executor.submit(() -> handler.accept(message));
    }
}
executor.submit() — Each handler runs on a thread pool worker, not the caller's thread. The publish call returns immediately. If a handler throws, it doesn't affect other handlers or the publisher.

Common Follow-ups

Message ordering guarantees?

With a thread pool, delivery order is non-deterministic — messages may arrive out of order at a subscriber. To guarantee order: use a single-threaded executor per topic, or assign each subscriber a dedicated queue with a single consumer thread. Kafka guarantees order within a partition.

Dead letter queue?

If a handler throws, the message is lost. A dead letter queue (DLQ) captures failed messages for retry or inspection. Wrap each handler in try-catch; on failure, add (topic, message, exception) to a DLQ. AWS SQS/SNS and RabbitMQ have built-in DLQ support.

At-least-once vs exactly-once?

At-most-once: fire and forget (current impl). At-least-once: retry on failure — may deliver duplicates. Exactly-once: requires idempotent consumers + deduplication (message IDs). Kafka achieves it with idempotent producers + transactional consumers. True exactly-once is the hardest distributed systems problem.

Distributed pub/sub (Kafka, SNS)?

Kafka: Persistent log per topic-partition. Consumers track offsets. Enables replay. SNS: Push-based fan-out to SQS, Lambda, HTTP. Redis: In-memory pub/sub — no persistence, messages lost if no subscriber online. The in-process version here is the conceptual building block for all of these.

Edge Cases & Gotchas

Publish to non-existent topic — getOrDefault(topic, List.of()) returns an empty list. No error, no delivery. Consider logging a warning for unregistered topics.
Handler throws exception — Since handlers run via executor.submit(), exceptions are silently swallowed (stored in the Future). Use CompletableFuture.runAsync() with .exceptionally() for visibility.
Backpressure — If publishers produce faster than subscribers consume, the executor's task queue grows unbounded → OOM. Use a bounded queue with a rejection policy (CallerRunsPolicy for natural backpressure).
Shutdown timing — executor.shutdown() waits for queued tasks to finish. Messages published during shutdown are still delivered. Use shutdownNow() for immediate stop (but may lose messages).
