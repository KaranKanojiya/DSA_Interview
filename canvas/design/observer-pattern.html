Core Idea

What is the Observer Pattern?

A one-to-many dependency: when a subject changes state, all registered observers are notified automatically. The subject (EventEmitter) doesn't need to know what the observers do — only that they implement update().

Also called: Listener, Callback, Publish-Subscribe (local variant).

Why use it?

  • Decoupling — subject & observers evolve independently
  • Open/Closed — add new observers without modifying the emitter
  • Event-driven — foundation for DOM events, React state, Spring listeners
  • Interviewers test understanding of loose coupling patterns

Operations — Step by Step

subscribe(event, observer)

  1. Look up event key in listeners map
  2. If no list yet → create new list via computeIfAbsent
  3. Add observer to the list

O(1) amortized — HashMap put + ArrayList add.

emit(event, data)

  1. Get observer list for event (or empty list)
  2. Iterate over all observers
  3. Call obs.update(event, data) on each

O(k) where k = number of observers for that event.

unsubscribe(event, observer)

Remove the specific observer from the event's list. Uses List.remove(Object) — O(k) scan. To make it O(1), use a Set instead of List.

EventEmitter — Fields

3

subscribe(event, observer)

register
void subscribe(String event, Observer observer) {
    listeners.computeIfAbsent(event, k -> new ArrayList<>()).add(observer);
}
computeIfAbsent — Creates the list only on first subscribe for that event. Cleaner than if-null-then-create boilerplate.
4

unsubscribe(event, observer)

deregister
void unsubscribe(String event, Observer observer) {
    List<Observer> obs = listeners.get(event);
    if (obs != null) obs.remove(observer);
}
5

emit(event, data)

notify all
void emit(String event, Object data) {
    for (Observer obs : listeners.getOrDefault(event, List.of())) {
        obs.update(event, data);
    }
}
List.of() returns an immutable empty list — avoids null checks. If no observers are registered, the loop simply doesn't execute.

Common Follow-ups

Async notification?

Wrap each obs.update() call in an ExecutorService.submit(). This decouples the emitter from slow observers — if one observer takes 5 seconds, it doesn't block the others. This is exactly what Pub/Sub adds over basic Observer.

Weak references to prevent leaks?

If observers are short-lived but forget to unsubscribe, the emitter holds strong references → memory leak. Use WeakReference<Observer> in the list. When GC collects the observer, the weak ref becomes null — clean up on next emit. Java's WeakHashMap can help.

Typed events with generics?

Instead of Object data, use generics: Observer<T> with update(T data). This provides compile-time type safety. The emitter becomes Map<Class<?>, List<Observer<?>>>. Guava's EventBus uses this approach with @Subscribe annotation.

React useState as Observer?

React's useState is an observer pattern: the component "subscribes" to state. When setState() is called (emit), React re-renders the component (notification). The virtual DOM diffing is the "update" method. This is why state changes trigger re-renders.

Edge Cases & Gotchas

ConcurrentModificationException — If an observer's update() calls subscribe() or unsubscribe() on the same event, you'll get a CME while iterating. Fix: iterate over a copy of the list, or use CopyOnWriteArrayList.
Observer exception kills emit — If one observer throws, subsequent observers won't be notified. Wrap each call in try-catch or use a defensive iteration pattern.
Observer vs Pub/Sub — Observer is synchronous and tightly coupled (subject knows observer interface). Pub/Sub adds a message broker in between, enabling async delivery and full decoupling. This repo's PubSubSystem is the next step.
Ordering guarantee — Observers are notified in registration order (ArrayList preserves insertion order). If you use a Set, order is non-deterministic.
