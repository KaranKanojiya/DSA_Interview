Logger — Implement from Scratch

Thread-safe singleton (double-checked locking + volatile) with configurable log levels (DEBUG / INFO / WARN / ERROR) and an Appender strategy for pluggable output targets. Uses ordinal() comparison for level filtering — messages below the minimum level are silently dropped.

Core Idea

What is it?

A singleton logger — one global instance shared across the entire application. Thread-safe via double-checked locking so only one instance is ever created, even under concurrent access.

Combines Singleton (single instance) + Strategy (swappable appender) patterns.

Why build from scratch?

  • Tests understanding of double-checked locking idiom
  • volatile keyword and memory visibility
  • Enum ordinal comparison for log level filtering
  • Strategy pattern for pluggable output (console, file, network)

Operations — Step by Step

getInstance()

  1. 1st null check — fast path, no locking
  2. If null → synchronized(Logger.class)
  3. 2nd null check inside lock — prevents race
  4. Create instance, assign to volatile field
  5. Subsequent calls skip both checks

log(level, msg)

  1. Compare level.ordinal() ≥ minLevel.ordinal()
  2. If below → silently return (filtered)
  3. Format: [time] [LEVEL] [thread] message
  4. synchronized(this) → appender.append()
  5. Appender strategy handles actual output

Level Enum & Appender Interface

contracts

Log levels use enum ordinal for filtering. Appender is a strategy interface — swap output target without changing the logger.

enum Level { DEBUG, INFO, WARN, ERROR }
// ordinals: DEBUG=0, INFO=1, WARN=2, ERROR=3

interface Appender {
    void append(String message);
}
// Strategy pattern — plug in console, file, network, etc.

getInstance() — Double-Checked Locking

thread-safe singleton
public static Logger getInstance() {
    if (instance == null) {                  // 1st check — no lock (fast path)
        synchronized (Logger.class) {       // class-level lock
            if (instance == null) {          // 2nd check — inside lock
                instance = new Logger();    // create once
            }
        }
    }
    return instance;
}
4

log(level, msg) — Level Filtering + Formatting

core method
public void log(Level level, String message) {
    if (level.ordinal() >= minLevel.ordinal()) {  // ordinal comparison
        String formatted = String.format(
            "[%s] [%s] [%s] %s",
            LocalDateTime.now().format(
                DateTimeFormatter.ofPattern("HH:mm:ss.SSS")),
            level,
            Thread.currentThread().getName(),
            message);
        synchronized (this) {
            appender.append(formatted);            // thread-safe output
        }
    }
}

Common Follow-ups

Log rotation?

File appender that rolls to a new file after size/time threshold. Track bytes written; when exceeding limit, close current file, rename with timestamp/index, open a new file. SLF4J/Logback provides RollingFileAppender with SizeBasedTriggeringPolicy and TimeBasedRollingPolicy.

Async appender?

Current implementation blocks the calling thread on appender.append(). Async solution: push formatted messages into a BlockingQueue, a dedicated writer thread drains and writes. Reduces latency on the calling thread. Logback's AsyncAppender uses a ring buffer (LMAX Disruptor) for lock-free queueing.

Structured logging (JSON)?

Instead of plain text, emit JSON: {"timestamp":"...","level":"INFO","thread":"main","message":"..."}. Enables machine parsing by log aggregation systems (ELK, Splunk, Datadog). Add MDC (Mapped Diagnostic Context) for request IDs, user IDs. Logback + logstash-logback-encoder is the standard Java approach.

SLF4J / Logback architecture?

SLF4J is a facade (interface only). Logback is the implementation. Architecture: Logger → Appender → Encoder → OutputStream. Logback supports: hierarchical loggers (com.example inherits from com), filters per appender, multiple appenders per logger. Configuration via logback.xml.

Log aggregation at scale?

Each service writes to local files or stdout → a log shipper (Filebeat, Fluentd) tails logs → pushes to a centralized store (Elasticsearch, CloudWatch, Splunk). The ELK stack: Elasticsearch (store + index), Logstash (transform), Kibana (visualize). Correlation IDs across services enable distributed tracing.

Edge Cases & Gotchas

volatile is mandatory — Without volatile, the JVM may reorder writes: another thread can see a non-null reference to a partially constructed Logger object. The volatile keyword establishes a happens-before edge.
Enum holder alternative — An inner static class Holder { static final Logger INSTANCE = new Logger(); } is simpler and thread-safe (class loading is synchronized by the JVM). No volatile or double-checked locking needed.
Enum singleton — enum Logger { INSTANCE; } is the simplest thread-safe singleton. Prevents deserialization and reflection attacks. Recommended by Effective Java but doesn't allow constructor parameters.
setLevel/setAppender thread-safety — These are simple field writes without synchronization. In a multi-threaded environment, make these fields volatile or guard with locks to ensure visibility. The current implementation relies on the synchronized block in log() for happens-before.
