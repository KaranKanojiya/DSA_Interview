Connection Pool — Implement from Scratch

Fixed pool of reusable connections using Semaphore (limits concurrency) + BlockingQueue (stores connections). getConnection() acquires a permit and polls; releaseConnection() offers and releases. The same pattern powers HikariCP, DBCP, and every production connection pool.

Core Idea

What is a Connection Pool?

A cache of pre-created, reusable connections (database, network, etc.). Instead of opening a new connection per request (expensive — TCP handshake, auth, TLS), you borrow one from the pool and return it when done.

Same pattern for thread pools, object pools, buffer pools.

Why Semaphore + BlockingQueue?

  • Semaphore — limits max concurrent borrows to pool size
  • BlockingQueue — thread-safe FIFO storage of idle connections
  • When pool exhausted, acquire() blocks the caller
  • No synchronized blocks needed — both primitives handle thread safety
2

Architecture Diagram

Why two primitives? The Semaphore gates access (blocks when all borrowed), while the BlockingQueue provides thread-safe storage. Together they give you a complete pool with zero synchronized blocks.
3

Operations — Step by Step

getConnection()

  1. semaphore.acquire() — blocks if no permits
  2. pool.poll() — take connection from queue
  3. Return connection to caller

If all connections are borrowed, the calling thread sleeps at step 1 until one is released.

releaseConnection(conn)

  1. pool.offer(conn) — return connection to queue
  2. semaphore.release() — give back permit
  3. A blocked thread wakes up and proceeds

Order matters: offer first, then release. Otherwise a thread could acquire a permit but find an empty queue.

Fields & Constructor

pool setup
private final BlockingQueue<Connection> pool;
private final Semaphore semaphore;

public ConnectionPool(int size) {
    pool = new LinkedBlockingQueue<>(size);
    semaphore = new Semaphore(size);

    // Pre-create all connections
    for (int i = 1; i <= size; i++) {
        pool.offer(new Connection(i));
    }
}
Semaphore(size) — Starts with size permits. Each getConnection() consumes one, each releaseConnection() returns one. When permits reach 0, acquire() blocks.
3

getConnection() — Borrow

acquire + poll
public Connection getConnection() throws InterruptedException {
    semaphore.acquire();          // blocks if no permits available
    Connection conn = pool.poll();  // take from queue (guaranteed non-empty)
    return conn;
}
4

releaseConnection(conn) — Return

offer + release
public void releaseConnection(Connection conn) {
    pool.offer(conn);       // return connection to queue
    semaphore.release();    // give back permit (wakes blocked thread)
}
Order: offer then release. If you release first, another thread's acquire() succeeds but pool.poll() might return null (the connection hasn't been offered yet). Offer first guarantees the queue is non-empty when the next thread polls.

Common Follow-ups

Health checks?

Before returning a connection from getConnection(), validate it (e.g., send a ping/SELECT 1). If invalid, discard it, create a new one, and offer it instead. HikariCP does this with connectionTestQuery or JDBC isValid().

Idle timeout eviction?

Track lastUsedTime on each connection. A background thread periodically scans the pool and closes connections idle beyond a threshold. This prevents holding stale connections that the database may have already closed (firewall timeouts, server-side idle limits).

Connection validation on borrow?

Two strategies: test-on-borrow (validate every get — safe but adds latency) vs test-while-idle (background validation — less overhead, small window for stale). HikariCP uses a hybrid: fast Connection.isValid() check on borrow with a configurable timeout. DBCP uses validationQuery.

HikariCP internals?

HikariCP uses ConcurrentBag — a lock-free, thread-local–friendly data structure. Each thread tries its thread-local list first (cache-friendly, no contention), then falls back to a shared CopyOnWriteArrayList, then creates a new connection if under max. It's the fastest Java pool because it minimizes CAS contention and avoids synchronized entirely.

Edge Cases & Gotchas

Connection leak — If a client forgets to call releaseConnection(), a permit is permanently lost → pool size effectively shrinks. Use try-finally or try-with-resources (AutoCloseable) to guarantee release.
Release order matters — offer(conn) before release(). Otherwise a woken thread may poll an empty queue. This is a subtle race condition.
Try-with-resources — Make Connection implement AutoCloseable where close() calls pool.releaseConnection(this). Then clients can write try (var conn = pool.getConnection()) { ... } — leak-proof.
Fairness — new Semaphore(size, true) uses a fair queue (FIFO). Without fairness, a thread that releases and immediately re-acquires can starve waiting threads. Fair semaphore has slightly higher overhead due to ordered queue.
