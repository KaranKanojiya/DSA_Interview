Consistent Hashing — Implement from Scratch

Distributes keys across nodes with minimal redistribution when nodes are added or removed. Uses a sorted TreeMap ring with virtual nodes for balance. Without consistent hashing: hash(key) % N → changing N moves ~all keys. With consistent hashing: adding/removing moves only ~1/N keys.

Core Idea

What is Consistent Hashing?

A technique that maps both keys and nodes (servers) onto the same hash ring. A key is assigned to the first node found clockwise from its hash position. Adding or removing a node only affects its immediate neighbors.

Used in distributed caches (Memcached, Redis Cluster), CDNs, load balancers, and distributed databases (DynamoDB, Cassandra).

Why virtual nodes?

  • With few physical nodes, hash distribution is uneven — some nodes get 60%+ of keys
  • Virtual nodes: each server gets V positions on the ring (e.g., Server-A-vn0, Server-A-vn1, …)
  • More positions → more uniform distribution
  • V = 100–200 is common in production

ceilingEntry(hash) — TreeMap's ceilingEntry(key) returns the entry with the smallest key ≥ given key. This is exactly "find the first node clockwise" on the ring. If null (past the max), wrap around with firstEntry().

Why Minimal Redistribution?

hash(key) % N

Adding a server changes N. Almost every key remaps to a different server. For 1M keys and 10 servers, ~90% of keys move.

Consistent Hashing

Adding a server only affects keys between it and its predecessor on the ring. For 1M keys and 10 servers, only ~10% of keys move (approximately 1/N).

ring setup

TreeMap provides sorted key order — perfect for clockwise lookup. virtualNodes count determines distribution quality.

private final TreeMap<Integer, String> ring = new TreeMap<>();
private final int virtualNodes;

addNode(node) — Place Virtual Nodes on Ring

O(V log N)
public void addNode(String node) {
    for (int i = 0; i < virtualNodes; i++) {
        int hash = hash(node + "-vn" + i);   // unique hash per vnode
        ring.put(hash, node);                // O(log N) TreeMap insert
    }
}
3

removeNode(node) — Remove All Virtual Nodes

O(V log N)
public void removeNode(String node) {
    for (int i = 0; i < virtualNodes; i++) {
        ring.remove(hash(node + "-vn" + i));  // O(log N) remove
    }
}
4

getNode(key) — Clockwise Lookup

O(log N)

The core operation: hash the key, find the nearest server clockwise using ceilingEntry, wrap around if needed.

public String getNode(String key) {
    if (ring.isEmpty()) return null;
    int hash = hash(key);
    // Find first node with hash ≥ key's hash (clockwise)
    Map.Entry<Integer, String> entry = ring.ceilingEntry(hash);
    if (entry == null) {
        entry = ring.firstEntry();   // wrap around the ring
    }
    return entry.getValue();
}

private int hash(String key) {
    return Math.abs(key.hashCode());
}

Common Follow-ups

Virtual node count tuning?

Too few vnodes (e.g., 3) → uneven distribution with hotspots. Too many (e.g., 1000) → more memory, slower add/remove. Sweet spot: 100–200 per node. With 150 vnodes and 10 servers, standard deviation of load drops from ~40% (no vnodes) to ~5%. Measure with real workloads.

Weighted nodes?

Give more powerful servers more virtual nodes (proportional to capacity). E.g., a 32GB server gets 200 vnodes, a 16GB server gets 100 vnodes. This naturally routes more keys to the bigger server. When upgrading hardware, just increase vnodes — only ~1/N keys redistribute.

Replication (N clockwise)?

For fault tolerance, replicate each key to the next N distinct physical nodes clockwise on the ring. Skip virtual nodes belonging to the same physical server. DynamoDB uses N=3 (preference list). If a node fails, its keys are already replicated on the next nodes — no data loss.

Distributed cache (Memcached/Redis Cluster)?

Memcached clients use consistent hashing client-side to pick a server per key. Redis Cluster uses a fixed 16384 hash slots — each node owns a range of slots. Adding a node migrates specific slot ranges. This is a variant of consistent hashing with explicit slot assignment rather than a ring.

Jump consistent hashing?

Google's jump consistent hash (2014): a stateless algorithm — no ring, no memory. Given a key and bucket count, returns the bucket in O(ln N) time. Perfectly balanced, minimal disruption. Limitation: only supports sequential bucket IDs (0..N-1), so not suitable when nodes join/leave by name. Best for numbered shards.

Edge Cases & Gotchas

Hash collisions on the ring — Two virtual nodes may hash to the same position. TreeMap.put overwrites the old entry. In production, use a high-quality hash (MD5, MurmurHash3) to minimize collisions. hashCode() is not ideal for uniform distribution.
Empty ring — getNode() must handle an empty ring (return null or throw). Always check ring.isEmpty() before calling ceilingEntry().
wrap-around via firstEntry() — When ceilingEntry(hash) returns null, the key's hash is larger than all nodes. Wrap around to firstEntry() — the "beginning" of the ring. This is the circular nature of the hash ring.
Better hash function — Java's hashCode() is not designed for uniform distribution. In production, use MurmurHash3 or MD5 (truncated to int). This dramatically reduces hotspots and virtual node collisions.
